# 账号与第三方登录方案

> 状态：已实现 | 更新：2026-11-24（修订 4）
>
> 本文只记录思路、设计与实施流程，不贴代码；具体实现以源码为准。

---

## 一、目标

在用户名 / 邮箱 + 密码登录之上，增加第三方一键登录（Apple、Google），并且：

- 老用户首次用第三方登录时，能自动关联到已有账号，不产生重复账号
- 并发与异常情况下不产生脏数据（无孤儿账号、无重复绑定）
- 换 client id 之类的运维动作，不需要重新构建前端产物

---

## 二、架构总览

| 项 | 选择 |
|---|---|
| 认证方式 | Django Session（无 JWT 会话、无 token 存储） |
| 用户模型 | Django 内置 User，不替换 AUTH_USER_MODEL |
| 认证后端 | 用户名精确匹配优先，否则按邮箱不区分大小写匹配 |
| 前端 | Vue 3 SPA，会话状态存于 reactive 对象 |
| 第三方登录 | id_token 校验模式，不引入第三方 OAuth 库 |

后端按域拆成两个 app：

| app | 职责 | 模型 |
|---|---|---|
| core | 健康检查、系统信息、SPA 入口 | 无 |
| accounts | 登录会话、第三方绑定、邮箱约束、用户档案 | SocialAccount、Profile |

拆分动机：后台分组按 app 划分，账号相关模型不该混在「核心」里；同时为后续的
用户档案等账号域模型留位置。

## 三、后端设计

### 3.1 数据模型

**SocialAccount —— 第三方账号绑定**

| 字段 | 说明 |
|---|---|
| user | 外键指向 User，删用户时级联 |
| provider | 提供方标识（apple / google） |
| provider_uid | 提供方返回的稳定用户标识（sub），长度按 512 预留 |
| extra_data | JSON，保存邮箱、显示名等登录时的快照 |
| created_at | 创建时间 |

约束：同一 provider 下的 uid 只能绑定一次（唯一约束）。

**Profile —— 用户档案（预留）**

与 User 一对一，字段包括显示名、头像地址（存 URL 而非上传文件，避免引入图片处理依赖）、
区域语言、创建与更新时间。

设计取舍：**不自动建行**，不挂用户创建信号。理由是把隐式写入挡在登录主链路之外，
需要时按需创建即可。后台已挂内联，可手工补填。

### 3.2 邮箱必填且唯一

**为什么需要**：登录支持用邮箱，第三方登录又按邮箱做自动关联。邮箱重复会让「匹配到哪个
账号」变成歧义。

**为什么放在数据库层**：内置 User 的 email 在模型层是可选字段，要改成必填必须替换
AUTH_USER_MODEL，代价过大。因此用两条数据库约束兜底：

- **唯一**：按小写比较，与「不区分大小写的邮箱匹配」保持一致
- **非空**：同时拒绝空串和纯空白

**应用层配合**（约束是最后一道防线，不能靠它产生用户可读的报错）：

| 场景 | 处理 |
|---|---|
| provider 未返回邮箱 | 拒绝建号，提示重新授权 |
| 邮箱已被其它账号占用 | 明确报错，提示先密码登录再绑定 |
| 后台新增 / 编辑用户 | 表单层就要求邮箱必填，避免撞约束变成 500 |
| 已绑定用户补写邮箱时撞约束 | 跳过补写，不影响登录 |

### 3.3 provider token 校验

Apple 与 Google 都是同一套思路：从提供方公钥端点取公钥，校验 RS256 签名与声明。

共同注意点：

- **公钥缓存**：公钥数月不变，客户端需缓存，避免每次登录都发 HTTP 请求；
  多 worker 部署下各自持有一份缓存，影响可忽略
- **必须校验签发方、受众、过期时间**：受众取各 provider 的 client id
- **email_verified 需要归一化**：Apple 返回的是字符串，不是布尔
- **Google 的 iss 有两种等价写法**，校验时要都接受
- 服务端未配置 client id 时应在发起网络请求之前就失败，给出明确提示

### 3.4 共用登录流程

provider 只负责「拿到稳定 uid、邮箱、显示名」，其余逻辑完全共用：

1. **已有绑定** → 校验账号启用状态 → 写会话
2. **未绑定，且邮箱已被 provider 核验** → 按邮箱唯一匹配已有账号 → 补建绑定 → 写会话
3. **需要新建账号** → 建用户与建绑定放在**同一个事务**里
4. **邮箱匹配到已有账号** → 只补建绑定（同样捕获并发冲突）
5. 写会话，返回用户信息

失败与边界：

| 情况 | 结果 |
|---|---|
| 未核验的邮箱命中已有账号 | **不关联**，继续走新建流程 |
| 新建时事务冲突，且另一请求已完成绑定 | 用对方的账号登录 |
| 新建时事务冲突，且没有绑定记录 | 判定邮箱被占用，返回冲突错误 |
| provider 未返回邮箱 | 拒绝建号 |
| 账号已被禁用 | 拒绝登录 |

三条关键设计：

- **孤儿账号已消除**。早期方案「先建用户、再建绑定」是两次提交，并发下第二个请求会留下
  无绑定的用户。现在两步同事务，冲突时一起回滚。
- **email_verified 是安全闸门**。只要邮箱匹配就绑定，等于允许任何人用未核验的邮箱接管
  他人账号。
- **建号不设密码**，由框架生成不可用密码，这类账号只能走第三方登录。

### 3.5 接口

全部挂在 /api/auth/ 下，命名空间 accounts。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | csrf/ | 下发 CSRF Cookie |
| GET | config/ | 前端运行时配置（两个 client id，未配置为空串） |
| GET | me/ | 当前用户，未登录 401 |
| POST | login/ | 用户名 / 邮箱 + 密码 |
| POST | logout/ | 登出 |
| POST | apple/ | 凭证 + 首次授权才有的显示名 |
| POST | google/ | 凭证（兼容另一种字段名） |

差异点：Google 的显示名在凭证里自带，前端无需额外传；Apple 的不在凭证里，只能由前端在
首次授权时单独提交。

### 3.6 前端运行时配置

client id 通过后端接口下发，**不使用前端构建期环境变量**。

理由：构建期变量会被编译成字面量写死进产物，换 id 就要重建、重打镜像；而这些 id 本来就是
公开信息（明文躺在产物里，浏览器可直接查看）。后端下发后，配置只有一处，换 id 只需重启
后端容器，且开发与生产行为一致。

判据：**读取者是构建工具 / dev server，或改它必须重新构建** → 留在前端环境变量；
**公开的运行时配置** → 走后端接口。

### 3.7 Admin

| 分组 | 模型 |
|---|---|
| 认证和授权 | 用户、组（框架自带） |
| 账号 | 第三方账号绑定、用户档案 |

- 用户表单在后台收紧为邮箱必填（模型层仍可选）
- 绑定表**不开放新增**：绑定必须由登录流程创建，手工新增容易造出指向错误用户的数据
- 用户详情页挂两个内联：第三方绑定（只读可删）、用户档案（可编辑）

## 四、前端设计

### 4.1 类型声明

两家 SDK 都是全局脚本注入，npm 上没有官方类型包，**必须自己声明**，否则类型检查无法通过、
构建失败。

### 4.2 按钮渲染策略

一律使用各家 SDK 的渲染方法，不手写 CSS 按钮：

- Apple 官方 HIG 要求（最小高度 44px、仅黑白两色、与第三方按钮同排时排首位）由 SDK 保证
- Google 的按钮样式由 SDK 统一维护

### 4.3 加载时序

1. 页面挂载 → 请求运行时配置
2. 等待一次渲染，确保按钮容器已进入 DOM（SDK 渲染方法需要真实元素）
3. 按需加载对应脚本，已存在同源脚本则跳过
4. 初始化并渲染按钮

**降级策略**：配置拉取失败、client id 为空、CDN 不可用，三种情况都只是「不渲染第三方按钮」，
密码登录始终可用。这是刻意设计——第三方登录是增强，不能成为登录页的单点故障。

### 4.4 前端环境变量职责

只放构建期 / dev server 需要的配置（例如开发代理指向哪个后端、接口根地址），
不再放第三方 client id。

## 五、配置要点

| 环境变量 | 说明 |
|---|---|
| GOOGLE_CLIENT_ID | Google OAuth 2.0 Web 客户端 ID，免费申请 |
| APPLE_CLIENT_ID | Apple Service ID；签名校验模式下不需要团队 ID 与密钥 ID |

两者都只有一处配置：仓库根目录的环境变量文件。未配置时前端不渲染按钮，直接调接口返回
「服务端未配置」类错误。

### 5.1 Google 配置步骤

1. 在 Google Cloud 创建凭据，应用类型选「Web 应用」
2. 「已获授权的 JavaScript 来源」填**实际访问页面的地址**，建议把开发端口和 127.0.0.1 变体
   一次填全——localhost 与 127.0.0.1 是不同来源，不能互相替代
3. 「已获授权的重定向 URI」留空：登录走弹窗回调，不跳转
4. 同意屏幕受众类型选**外部**；测试状态下只有测试用户名单里的账号能登录
5. 本项目只用基础资料类 scope，属于非敏感范围，**发布到生产不需要审核**
6. 「用于 AI Agent」之类的选项与登录无关，不要勾选

### 5.2 Apple 现状

Web 端「使用 Apple 登录」需要先创建 Service ID，而这一步所在的开发者后台页面对**免费账号
不可用**，会直接提示「Access Unavailable」——只有加入付费的 Apple Developer Program
（99 美元 / 年）才能访问。

因此当前状态是：**Apple 相关代码、类型声明、按钮逻辑全部保留可用，但 client id 未配置，
按钮不渲染**。一旦拿到 Service ID 填入环境变量并重启后端即可启用，无需改代码。

### 5.3 网络前提（重要）

- 前端弹窗需要浏览器能访问 accounts.google.com
- 后端校验 token 需要访问 www.googleapis.com 的公钥端点
- **容器不继承宿主机的系统代理**，若宿主机依赖代理访问 Google，需要单独为 web 服务注入
  代理环境变量，且代理排除列表必须包含数据库主机，否则容器连不上数据库

从中国大陆直连时，Google 的两个域名不可达，而 Apple 的域名可达。若目标用户集中在国内网络
环境，Google 登录需要用户自备代理，Apple 登录反而不需要——这个取舍需要在产品层面判断。

## 六、端到端流程

1. 用户点击第三方登录按钮
2. 提供方弹窗完成授权，前端拿到凭证
3. 前端把凭证提交给后端
4. 后端校验签名与声明，走第三节的共用登录流程
5. 后端写会话并返回用户信息
6. 前端跳转到来源页或首页；跳转目标只接受站内以斜杠开头的路径，防开放重定向

## 七、设计决策

| 决策 | 理由 |
|---|---|
| 不引入第三方社交登录库 | 项目精简，手动校验更可控 |
| 公钥客户端缓存 | 避免每次登录都发 HTTP 请求 |
| provider 无关的共用登录流程 | Apple 与 Google 只差凭证校验，其余逻辑完全一致 |
| 独立的绑定表 | 不动内置 User，唯一约束防止同一身份被绑定两次 |
| id_token 校验模式 | 前端拿凭证、后端只验签名声明，无需维护刷新令牌 |
| 邮箱自动关联 + 核验闸门 | 减少用户操作，同时不允许用未核验邮箱接管账号 |
| 不自动合并同邮箱多账号 | 保护数据完整性，拒绝模棱两可的情况 |
| 建用户与建绑定同事务 | 消除并发下的孤儿账号 |
| 邮箱约束下沉到数据库 | 不改 AUTH_USER_MODEL，同时让「必填 + 唯一」成为硬约束 |
| client id 运行时下发 | 换 id 不必重建前端产物 |
| 账号域独立成 app | 后台分组按 app 划分，也为后续账号域模型留位置 |
